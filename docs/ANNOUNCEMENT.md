## Hacker News — "Show HN"

**Title** (80 char limit; the number and the honesty both need to fit):

> Show HN: toolgz – cut LLM tool-definition tokens ~80% without hurting accuracy

Alternates:
> Show HN: I compressed my agent's tool definitions by 80% and was wrong about why it worked
> Show HN: toolgz – 720 benchmark runs on whether compressing tool schemas breaks tool use

**Body:**

If you wire an agent to a few MCP servers, you'll notice tool definitions eating
your context window before the user says anything. Each tool is a JSON Schema
with a sentence of prose per parameter; ~420 tokens each is normal. Fifty tools
is 20k tokens at the front of every request.

toolgz compresses that block and translates the model's calls back, so your
dispatcher receives the same tool name and arguments it did before.

I expected this to fail. The aggressive mode replaces `github_search_issues`
with `a0` and puts a lookup table in the (cached) system prompt, and my strong
prior was that stripping the semantic name would wreck tool selection. So I
built the benchmark to catch that, with deliberately confusable clusters —
`search_issues` vs `list_issues`, comment-vs-update, approve-vs-merge, three
products with identically-shaped tools side by side.

It didn't fail. 720 runs across `claude-opus-5`, `gpt-5.6-sol`,
`gemini-3.1-pro-preview` and `grok-4.5`, reasoning enabled on all four:

- Prompt tokens: **−69% to −82%** depending on provider
- Tool-definition block: **−79% to −88%**
- Tasks completed: **60/60**, zero hallucinated tool names

The mechanism seems to be that the model converts a recall problem into a
retrieval problem. It doesn't need the name in context; it needs a way to find
it, and it'll spend a lookup call to do so.

Three things I'd want to know if I were reading this:

**1. Cost does not always go down.** Context always shrinks. Spend fell 60–76%
on three providers and **rose 15% on OpenAI** — the dispatcher's extra turns
cost more in reasoning tokens than the smaller prompt saves. If your constraint
is context window this wins everywhere; if it's the bill, measure your own
workload. The README says this in the third chart rather than the footnotes.

**2. A bare-name map failed on Grok, deterministically.** Not noise: one
scenario, 3 of 3 attempts, `turns=1`, zero tool calls, no error raised — the
model read the map and answered without dispatching. Adding the required
argument names to each map line fixed it 3/3 and is now the default. Same shape
as failure #3.

**3. Anthropic's own `defer_loading` tool search completed 6/30 tasks on
Haiku 4.5** — silently, for the same reason. Deferred loading makes tool
discovery *optional*; a small model can decline to discover and answer unaided.
A dispatcher makes discovery the entry point, which is a structural difference
rather than a tuning one. On Opus 5, `defer_loading` was a clean 20/20 — this
only shows up below the frontier tier.

What it costs you: at the aggressive level the model fills a generic argument
object, so the provider's constrained sampler no longer enforces your schema.
The library validates against your original schema and hands the model a
readable error instead. On Haiku 4.5 that fired on 17 of 30 runs — every one
caught and retried, no task lost, but that's the real edge.

Every per-run record is committed in the repo, so you can recompute any figure
rather than trust it. The before/after docs are generated by running the library,
with a test asserting they match the code. TypeScript, zero runtime
dependencies, Apache-2.0.

I'd particularly like to be argued with on the OpenAI cost result and on whether
the confusable-tool suite is actually hard enough.

I spent this week trying to prove my own idea wrong, and failed. So I'm shipping
it.

If you're building AI agents, you've probably hit this: connect a handful of MCP
servers and your tool definitions eat 30–50k tokens of context before the user
types a word. Each tool is a JSON Schema with a sentence of prose for every
parameter. Fifty tools is 20,000 tokens, sitting at the front of every single
request.

Prompt caching makes those tokens cheap. It doesn't make them take up less room.

So I built **toolgz** — it compresses the tool block and translates the model's
calls back, so nothing downstream changes.

The aggressive mode does something that sounds reckless: it replaces
`github_search_issues` with `a0` and puts a lookup map in the cached system
prompt. I was confident this would make models worse at picking the right tool,
and I built the benchmark specifically to catch that — deliberately confusable
tool clusters where the correct answer hinges on the name being taken away.

**720 runs across four frontier models later:**

→ 69–82% fewer prompt tokens
→ 79–88% smaller tool-definition block
→ 60/60 tasks completed, zero hallucinated tool names

I was wrong. The model doesn't need the name in its context — it needs a way to
look it up, and it will spend one call to do that.

Two things I'm publishing that don't flatter the result, because they're true:

**Cost doesn't always drop.** Context always does. But on OpenAI the bill went
*up* 15% — the extra dispatcher turns cost more in reasoning tokens than the
smaller prompt saves. If your constraint is the context window, this wins
everywhere. If it's spend, measure your own workload first.

on Grok in a very specific way: the model read the map and answered with no tool
call at all — no error, just an unaided answer. Adding the required argument
names to each line fixed it completely. That failure mode turned out to be the
same one that makes Anthropic's own deferred tool loading complete only 6 of 30
tasks on their small model. When you make tool discovery *optional*, a model can

Every benchmark run is committed to the repo. The before/after documentation is

## What not to say

Guard-rails for anyone else writing about this:

- ❌ "80% cheaper" — it is not. Cost rose 15% on OpenAI. The claim is
  **context-window occupancy**.
- ❌ "Works on any model" — measured on four frontier models from four vendors.
  Below the frontier tier, argument errors rise sharply (17/30 runs on
  Haiku 4.5, all recovered).
- ❌ "Beats Anthropic's tool search" — it does not beat it on tool-block size.
  It composes with it, and is more reliable below the frontier tier.
- ❌ "Lossless" — at levels 2–3 you give up provider-side constrained decoding.
  The library replaces that guarantee with its own validation; that is a
  trade, not a free lunch.
- ❌ Any figure not in [RESULTS.md](RESULTS.md). Every number there is
  recomputable from committed data.
